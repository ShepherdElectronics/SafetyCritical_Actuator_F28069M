The next layer is Allan deviation / Allan variance analysis.
What Allan deviation does for this project

For SDC2, Allan deviation answers:

How does encoder-derived position/speed noise change as I average over longer times?
At what averaging time does noise improve?
When does drift start dominating?
Is the platform stable enough for the sensing-medium tests?

That matches the test protocol exactly: the protocol says the motion-platform output should be determined separately before combining it with the sensing medium, and that the analysis should follow the Allan Variance / Allan Deviation approach used for IMUs, gyros, and accelerometers. It also says datasets may be large and should be saved as separate CSV files for offline analysis.
Which SDC2 datasets get Allan deviation?

Primarily these:
Dataset	Allan signal to analyze	Purpose
STATIC_50HZ_HOLD	ActualTablePosition_deg or derived rate	drift/noise while holding still
STATIC_100HZ_HOLD	ActualTablePosition_deg or derived rate	check higher-frequency noise
Constant-speed trials	speed error or position following error	bias, repeatability, speed-dependent error
Sine trials	following error vs command	inertial/following-error behavior

For static tests, the Allan documents are directly relevant: Allan deviation is useful because ordinary standard deviation does not cleanly separate white noise, flicker/noise floor, random walk, and drift. Land et al. specifically contrast standard deviation with Allan deviation, explaining that Allan deviation gives magnitude-versus-time separation on a log-log plot so different noise/drift regions can be identified by slope.
How to interpret the Allan plots

On the log-log Allan deviation plot:
Slope	Meaning
-0.5	white noise averaging down
0	flicker/bias-instability-like floor
+0.5	random walk / slow wandering
+1	steady drift / ramp

Land et al. give this same practical interpretation: Gaussian noise appears with slope -0.5, flicker noise with slope 0, random-walk noise with slope +0.5, and linear drift trends toward slope +1.

So for your static SDC2 data, the plot will tell you something like:

Short tau: encoder quantization / white noise
Middle tau: best averaging region / bias stability floor
Long tau: thermal drift, mechanical creep, cable/load drift, or table wandering

That is exactly why the first two no-motion tests matter.
One important correction

For Allan analysis, do not treat the whole 37-minute all-trials file as one continuous Allan dataset. That file contains deliberate motion changes, speed changes, and sine commands.

Use Allan deviation on individual labeled segments, especially:

STATIC_50HZ_HOLD
STATIC_100HZ_HOLD
each constant-speed trial separately

The “Allan Deviation Made Simple” document says that for noise characterization, the input parameter should be held constant and preferably zero; otherwise actual dynamic input changes become mixed into the “noise” estimate.

I thought our encoder had much higher resolution than this 

It does have higher position resolution. The plot looks chunky because you are plotting encoder-derived velocity, and velocity resolution is much worse than position resolution when the motion is ultra slow.

Your encoder/table position resolution is about:

1 count ≈ 0.00146 deg at the output/table

That part is good.

But speed is calculated from:

measured speed = Δposition / Δtime

So if the speed estimate window is too short, the encoder can only report speeds in chunks of:

1 count / time window

For example, with 1 count = 0.00146 deg:
Speed averaging window	Smallest nonzero speed jump
0.1 s	0.0146 deg/s
0.25 s	0.00584 deg/s
0.5 s	0.00292 deg/s
1.0 s	0.00146 deg/s
2.0 s	0.00073 deg/s
5.0 s	0.000292 deg/s
10.0 s	0.000146 deg/s

Your plot shows the measured speed jumping in bands around:

0.005–0.011 deg/s

That is exactly what I’d expect if the speed estimate is using a short window and only seeing a few encoder counts per window.

At 0.005 deg/s, the encoder only advances:

0.005 deg/s / 0.00146 deg/count ≈ 3.4 counts/s

At 0.01 deg/s:

0.01 deg/s / 0.00146 deg/count ≈ 6.85 counts/s

So even though position resolution is good, velocity estimation at these speeds is fundamentally count-limited unless you average over several seconds.

For boss-ready plots, don’t show raw instantaneous encoder speed as the main proof. Show:

1. Position vs time
2. Best-fit line through position
3. Residual = position - best-fit line
4. Average speed from slope

That will look much cleaner and more honest.

For your MATLAB speed plot, replace the short-window/raw speed with a longer smoothing window, like 5–10 seconds for 0.005–0.01 deg/s.

function colName = findCol(vars, candidates)
    colName = findColOptional(vars, candidates);
    if colName == ""
        error("Could not find required column. Tried: %s", strjoin(candidates, ", "));
    end
end

function colName = findColOptional(vars, candidates)
    colName = "";

    for c = candidates
        idx = find(strcmpi(vars, c), 1);
        if ~isempty(idx)
            colName = vars(idx);
            return;
        end
    end

    for c = candidates
        idx = find(startsWith(lower(vars), lower(c)), 1);
        if ~isempty(idx)
            colName = vars(idx);
            return;
        end
    end
end

function y = signOrOne(x)
    if x < 0
        y = -1;
    else
        y = 1;
    end
end

function colName = findCol(vars, candidates)
    colName = findColOptional(vars, candidates);
    if colName == ""
        error("Could not find required column. Tried: %s", strjoin(candidates, ", "));
    end
end

function colName = findColOptional(vars, candidates)
    colName = "";

    for c = candidates
        idx = find(strcmpi(vars, c), 1);
        if ~isempty(idx)
            colName = vars(idx);
            return;
        end
    end

    for c = candidates
        idx = find(startsWith(lower(vars), lower(c)), 1);
        if ~isempty(idx)
            colName = vars(idx);
            return;
        end
    end
end

function y = signOrOne(x)
    if x < 0
        y = -1;
    else
        y = 1;
    end
end

    rawFile = string(files(idxNewest).name);
end

timeCol   = findCol(vars, ["Time_s","Time"]);
targetCol = findCol(vars, ["TargetSpeed_deg_s","TargetSpe","TargetSpeed"]);
countCol  = findCol(vars, ["EncoderCount","Encoder"]);
stateCol  = findColOptional(vars, ["State"]);
faultCol  = findColOptional(vars, ["FaultCode","Fault"]);

targetAll = T.(targetCol);
speeds = unique(targetAll);
speeds = speeds(~isnan(speeds));
speeds = speeds(speeds > 0);

fprintf("Target speed sections found:\n");
disp(speeds');

Summary = table();

    idx = abs(targetAll - s) < 1e-12;

    if nnz(idx) < minRowsPerSegment
        continue;
    end

    S = T(idx,:);

    tRaw = S.(timeCol);
    cRaw = S.(countCol);

    % Local segment time and count
    t = tRaw - tRaw(1);
    c = cRaw;
    cDelta = c - c(1);

    duration = t(end) - t(1);
    totalCountDelta = c(end) - c(1);

    expectedCountsPerSec = abs(s) / degPerCount;
    expectedDt = 1 / expectedCountsPerSec;
    expectedCountDelta = expectedCountsPerSec * duration;

    measuredCountsPerSec = abs(totalCountDelta) / duration;
    measuredAverageSpeed = measuredCountsPerSec * degPerCount;
    speedRatio = measuredAverageSpeed / abs(s);
    countRatio = abs(totalCountDelta) / expectedCountDelta;

    %% Event extraction from raw EncoderCount changes

    dcSample = diff(c);
    eventIdx = dcSample ~= 0;

    eventTimes = t(2:end);
    eventTimes = eventTimes(eventIdx);

    eventCounts = c(2:end);
    eventCounts = eventCounts(eventIdx);

    if numel(eventTimes) >= 2
        eventDt = diff(eventTimes);
        eventCountJump = abs(diff(eventCounts));
        eventSpeed = eventCountJump * degPerCount ./ eventDt;
        eventTimes2 = eventTimes(2:end);

        meanDt = mean(eventDt, "omitnan");
        medianDt = median(eventDt, "omitnan");
        stdDt = std(eventDt, "omitnan");
        minDt = min(eventDt);
        maxDt = max(eventDt);

        meanEventSpeed = mean(eventSpeed, "omitnan");
        medianEventSpeed = median(eventSpeed, "omitnan");
        stdEventSpeed = std(eventSpeed, "omitnan");

        highDtIdx = eventDt > dtRatioWarnHigh * expectedDt;
        lowDtIdx  = eventDt < dtRatioWarnLow  * expectedDt;

        badSpeedIdx = eventSpeed < speedRatioGoodLow * abs(s) | ...
                      eventSpeed > speedRatioGoodHigh * abs(s);

        numLongGaps = nnz(highDtIdx);
        numShortGaps = nnz(lowDtIdx);
        numBadSpeedEvents = nnz(badSpeedIdx);
    else
        eventDt = [];
        eventSpeed = [];
        eventTimes2 = [];

        meanDt = NaN;
        medianDt = NaN;
        stdDt = NaN;
        minDt = NaN;
        maxDt = NaN;

        meanEventSpeed = NaN;
        medianEventSpeed = NaN;
        stdEventSpeed = NaN;

        lowDtIdx = [];
        badSpeedIdx = [];

    ax.GridAlpha = 0.28;

            'LineWidth', 1.2, ...

function colName = findCol(vars, candidates)
    colName = findColOptional(vars, candidates);
    if colName == ""
        error("Could not find required column. Tried: %s", strjoin(candidates, ", "));
    end
end

function colName = findColOptional(vars, candidates)
    colName = "";

    for c = candidates
        idx = find(strcmpi(vars, c), 1);
        if ~isempty(idx)
            colName = vars(idx);
            return;
        end
    end

    for c = candidates
        idx = find(startsWith(lower(vars), lower(c)), 1);
        if ~isempty(idx)
            colName = vars(idx);
            return;
        end
    end
end

function y = signOrOne(x)
    if x < 0
        y = -1;
    else
        y = 1;
    end
end

A true cascaded controller would be more professional:

Outer position loop:
  position error -> desired velocity correction

Inner velocity loop:
  velocity error -> step-rate correction

But for ultra-slow encoder data, the inner velocity loop should use event timing, not noisy gradient(position). Something like:

Encoder count event dt -> measured event speed -> low-bandwidth velocity correction

Best next controller architecture:

1. Feedforward step rate sets the main scan speed.
2. Acceleration ramp prevents stalls.
3. Outer position loop slowly corrects accumulated drift.
4. Inner velocity/event loop gently corrects speed ripple.
5. Correction limits prevent the loop from chasing encoder quantization.

The important caution: don’t make the PID aggressive. At these speeds, encoder counts are discrete, so too much gain will create jitter. Use the PID as a slow trim, not a hard chase.
